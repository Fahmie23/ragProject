# LangChain integration example

This directory shows how **RAG Document Studio's existing retrieval pipeline** can be exposed through LangChain without rewriting the evaluated production architecture.

The core application intentionally owns document processing, BGE-M3 embeddings, PostgreSQL full-text search, RRF fusion, BGE reranking, bounded structural context, deterministic citations, provenance, and visual evidence. This example wraps that retrieval behavior behind LangChain's standard `BaseRetriever` interface and composes it with LCEL plus `ChatGroq`.

```text
Question
   ↓
RagDocumentStudioRetriever (LangChain BaseRetriever)
   ↓ HTTP
/api/retrieval/hybrid-rerank-context
   ↓
Production BGE-M3 + PostgreSQL FTS + RRF + reranker
   ↓
LangChain Documents
   ↓
LCEL prompt → ChatGroq → StrOutputParser
   ↓
Answer + retrieved Document objects
```

## Why this is an adapter instead of a rewrite

A framework integration should not silently change the system being evaluated. The retriever therefore calls the same RAG Document Studio endpoint used by the production retrieval path instead of rebuilding dense search, lexical search, fusion, or reranking inside LangChain.

That gives this portfolio both:

- direct control and evaluation of the underlying RAG mechanics; and
- a concrete example of mapping those mechanics into an industry-standard LangChain interface.

## Files

| File | Purpose |
| --- | --- |
| `retriever.py` | Implements `RagDocumentStudioRetriever(BaseRetriever)` and maps API hits/context chunks to LangChain `Document` objects. |
| `chain.py` | Composes retrieval, prompt construction, `ChatGroq`, and parsing with LCEL. |
| `demo.py` | Small CLI for running the adapter against an already-ingested document. |
| `requirements.txt` | Isolated optional dependencies; no LangChain dependency is added to the production backend. |

## Setup

Start the normal application first:

```bash
cd ~/ragProject
docker compose up -d
curl -s http://localhost:8000/health
```

Create an isolated environment for the example:

```bash
cd ~/ragProject/examples/langchain
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Export the Groq key in the shell running the demo. Do not commit it:

```bash
export GROQ_API_KEY="your-key"
```

Optionally select another Groq-hosted model:

```bash
export LANGCHAIN_GROQ_MODEL="openai/gpt-oss-120b"
```

## Run

Use an existing document that already has chunks and embeddings:

```bash
python demo.py \
  --document-id 485c4989-c300-45c8-ac06-79a59492bb5c \
  --question "Explain the BbRA and RbRA process."
```

The demo prints the LangChain-generated answer followed by the retrieved `Document` objects and their page/section metadata.

## What this demonstrates

- custom `BaseRetriever` implementation;
- conversion of an existing retrieval service into LangChain `Document` objects;
- LCEL / Runnable composition;
- provider integration through `ChatGroq`;
- preservation of page, section, chunk, source-element, and visual-reference metadata;
- separation between framework orchestration and the underlying retrieval implementation.

## Important trust boundary

The `[LC1]`, `[LC2]`, ... labels in this example are **prompt-level citations generated by the model**. They are useful for demonstrating a conventional LangChain RAG chain, but they do **not replace** RAG Document Studio's production citation system.

The main application derives citations and provenance deterministically from backend evidence after generation. For portfolio evaluation, the production `Search & Ask` path remains the authoritative implementation.
